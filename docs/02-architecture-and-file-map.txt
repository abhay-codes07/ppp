2.1 Two products in one repository
----------------------------------
PRODUCT A: the WORKFLOW ENGINE. You describe a process as a Petri net (places, transitions,
tokens), attach guards and executors to transitions, and a Scheduler runs it with SQLite
persistence. The CLI analyses the net before it runs.

PRODUCT B: the TOOL GATE. You describe which tool calls an AI agent may make, in which order,
as small Petri nets (SkillNets). Adapters plug the gate into agent frameworks. A rules DSL
compiles one-line rules into those nets.

Both sit on one external library: petri-ts (v0.2.0, 208 lines of JavaScript) which holds the
actual Petri-net mathematics: canFire, fire, reachableStates, terminalStates, isDeadlockFree,
checkInvariant, analyse.

2.2 Dependency chain
--------------------
    petri-ts (external)
      -> @petriflow/engine        (workflow engine; re-exports petri-ts)
           -> @petriflow/gate     (tool gate core: SkillNet, GateManager, 4-phase decision)
                -> @petriflow/rules        (DSL compiler -> SkillNets)
                -> @petriflow/vercel-ai    (wrapTools, replay from messages)
                -> @petriflow/agent-sdk    (Claude Agent SDK hooks, in-process)
                -> @petriflow/claude-code  (hook process, state in /tmp JSON)
                -> @petriflow/petriflow-gate  (folder packages/openclaw; OpenClaw plugin)
                -> @petriflow/pi-extension -> @petriflow/pi-assistant (hand-written nets)
           -> @petriflow/cli      (petriflow analyse)
           -> apps/viewer         (React + xyflow visualiser)

Packages import each other through dist/, so `bun run build` must run before `bun test`.

VERIFIED QUIRK: packages/gate/package.json asks for "@petriflow/engine": "^0.1.3". The
workspace engine is 0.3.0, so Bun installs a nested copy packages/gate/node_modules/
@petriflow/engine at 0.1.3, which bundles petri-ts 0.1.6. The analysis path (rules, engine,
CLI) uses petri-ts 0.2.0. The runtime gate uses the nested 0.1.6 canFire/fire. Two versions of
the core maths are live in one install. For normal nets they behave the same.

2.4 One tool call, end to end (diagram 13)
------------------------------------------
1. The LLM picks a tool. The adapter intercepts (wrapTools execute wrapper, or a hook).
2. GateManager.handleToolCall -> composedToolCall over all active nets:
   Phase 1 classify, per net: resolvedTool = toolMapper(event) or the name.
     in freeTools                      -> FREE
     no transition lists the tool      -> ABSTAIN (net has no opinion)
     listed, but none canFire          -> BLOCKED
     listed and some canFire           -> GATED (first matching transition)
   Any BLOCKED -> block with formatBlockReason text. No GATED -> allow.
   Phase 2 approvals: for each gated MANUAL transition, if !ctx.hasUI block; else await
     ctx.confirm(); a "no" blocks.
   Phase 3 validate: snapshot meta; run each net's validateToolCall; on reject, roll back
     meta of nets already validated and block.
   Phase 4 commit: re-check canFire (state may have moved during the awaits: TOCTOU);
     deferred -> record in pending[toolCallId]; else fire, then autoAdvance.
3. The tool runs (real side effect).
4. handleToolResult: pop pending; if !isError and canFire -> fire deferred transition,
   onDeferredResult, autoAdvance. On error: forget the pending entry; nothing fires.
5. Blocked calls surface to the model as a tool error with the reason text, so it can
   choose the unlocking action.

2.5 The workflow engine tick (diagram 20)
-----------------------------------------
Scheduler.tick(): load instances from the persistence adapter -> for each: fire expired
timeouts (add tokens) -> executor.step or stepBatch (guards evaluated here, decision
provider if several enabled) -> schedule timeouts for newly enabled transitions -> persist
marking, context, history with an optimistic version check -> mark completed when a
terminal place holds a token, failed when an executor throws.

2.6 What the gate does NOT use at runtime
-----------------------------------------
packages/gate/src imports only canFire and fire from the engine. It never calls
reachableStates, analyse or checkInvariant. The `guard` field on GatedTransition is declared
but never evaluated by the gate. terminalPlaces is never read by the gate. The analysis
result influences nothing at runtime; it is information for the developer.

2.7 State between calls, per adapter
------------------------------------
vercel-ai    in memory per wrapTools() call; across HTTP requests the CALLER passes
             messages and replay rebuilds the marking from tool-call/tool-result pairs.
             Replay fires transitions directly, skipping manual approval and
             validateToolCall. Pending deferred calls are not carried over.
claude-code  a fresh process per hook event; JSON file in /tmp; read-modify-write without
             locks; SessionStart deletes the file.
agent-sdk    one in-process manager per createPetriflowGate(); one gate per conversation.
openclaw     one in-process manager per plugin registration; synthetic ids, FIFO matching.
pi-extension one in-process manager per composeGates(); removed nets keep their state.
engine       SQLite with versioning (the only durable, concurrency-aware store).
