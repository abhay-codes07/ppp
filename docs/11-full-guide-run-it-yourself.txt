Step 3.1 Coffee: two parallel branches and a join
bun run workflows/coffee/index.ts
Expected output (takes about 6 seconds because executors sleep)
[brew-001] fired: heatWater
  context: { waterTemp: 96, grindSize: "none", brewed: false }
[brew-001] fired: grindBeans
  context: { waterTemp: 96, grindSize: "medium", brewed: false }
[brew-001] fired: pourOver
  context: { waterTemp: 96, grindSize: "medium", brewed: true }
[brew-001] v completed
Final state: { marking: { ..., coffeeReady: 1 }, status: "completed" }
WHAT IS EXECUTING
Tick 1: enabled = [heatWater, grindBeans]. No decision provider is set, so step() picks the first, heatWater; its
execute sleeps 2 s and returns {waterTemp: 96}. Tick 2: grindBeans. Tick 3: pourOver is now enabled (three input
tokens) and its guard 'waterTemp >= 90' passes. Tick 4: nothing enabled, no timers, status becomes completed,
the loop breaks. Each tick saved a row to SQLite and appended to transition_history.
IN SIMPLE WORDS Why did heatWater go first?
Because it is listed first in definition.ts and no decision provider is configured. The analyser treats both orders as
possible (5 reachable states). The runtime picked one. That gap between 'all possible' and 'what happened' is the
whole point of analysing before running.

Part 4. Drive the safety gate by hand (no API
key)
This is the most useful lab in the guide. A 40-line script compiles three rules, builds a GateManager, and
calls it the way an adapter would. You watch every verdict and every marking change.
Step 4.1 Create the script
Create a folder labs in the repo root and save this as labs/gate-playground.ts. The repo root
resolves @petriflow/* because of the workspace links from step 1.3.
mkdir -p labs
cat > labs/gate-playground.ts <<'EOF'
// Lab: play with the gate without any API key.
// Run from the repo root:  bun run labs/gate-playground.ts
import { compile } from "@petriflow/rules";
import { createGateManager } from "@petriflow/gate";
// 1. Compile three rules. Each becomes one small Petri net.
const { nets, verification } = compile(`
  require backup before delete
  block rm
  limit push to 2 per session
`);
console.log("Compiled nets:", nets.map((n) => n.name));
console.log("Verification (reachable states per net):", verification);
// 2. Build a manager. "enforce" means blocked calls really get blocked.
const manager = createGateManager(nets, {
  mode: "enforce",
  onDecision: (event, decision) => {
    const verdict = decision?.block ? `BLOCK (${decision.reason})` : "allow";
    console.log(`  decision for ${event.toolName}: ${verdict}`);
  },
});
const ctx = { hasUI: false, confirm: async () => false };
function status() {
  return manager.formatStatus().replace(/\n/g, " | ");
}
async function call(id: string, toolName: string) {
  console.log(`\n> agent calls ${toolName}`);
  await manager.handleToolCall({ toolCallId: id, toolName, input: {} }, ctx);
  console.log("  state:", status());
}
// 3. Walk a scenario.
await call("c1", "delete");   // blocked: no backup yet
await call("c2", "backup");   // allowed, but deferred (not fired yet)
console.log("  (backup tool is running...)");
manager.handleToolResult({
  toolCallId: "c2", toolName: "backup", input: {}, isError: false,
});
console.log("  backup succeeded -> deferred transition fired");
console.log("  state:", status());
await call("c3", "delete");   // allowed now
await call("c4", "delete");   // blocked again: needs a new backup
await call("c5", "rm");       // always blocked
await call("c6", "push");     // 1 of 2
await call("c7", "push");     // 2 of 2
await call("c8", "push");     // over the limit
await call("c9", "ls");       // no net cares: passes
console.log("\nSystem prompt the LLM would see:");
console.log(manager.formatSystemPrompt());

EOF
Paste the whole block including the final EOF line. Git Bash will create the file.

WHAT IS EXECUTING
Line by line: compile() parses three lines and returns three SkillNets plus their state counts.
createGateManager creates one GateState per net and runs autoAdvance, which is why every net already
shows 'ready:1' and not 'idle:1'. Each handleToolCall runs classifyNets: for 'delete' the first net has jurisdiction
but no enabled transition (blocked), the other two abstain. For 'backup' the first net is gated with a deferred
transition, so the call is allowed but the marking waits for handleToolResult. 'ls' appears in no net, so all three
abstain and it passes. The push budget is visible as a token count that drops to zero.
IN SIMPLE WORDS Things to try next
Change isError: false to isError: true on the handleToolResult line and run again: delete stays blocked because a
failed backup does not count. Add a line require human-approval before push to the rules: every push is now
blocked because the script passes hasUI: false. Change mode: "enforce" to "shadow": onDecision still prints
BLOCK but nothing is actually blocked.

Part 6. Break a proof on purpose
The fastest way to understand what the tests prove is to make them fail. This experiment adds a shortcut
that bypasses the human approval in the agent benchmark, then watches which checks notice.

LOOPHOLE The CLI did not notice
--strict only checks for unexpected terminal states and invariant violations. A bypassed human gate is neither.
Domain properties like 'code never runs without approval' live only in the test file. If you adopt this engine, the
property tests are the real safety net, and they must be written per workflow.
