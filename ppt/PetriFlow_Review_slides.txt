SLIDE 4: Where should the rule live?
------------------------------------------------------------------------------
  [diagram: 01-where-the-rule-lives.png]
  Prompts, deny lists and if-statements each leak. PetriFlow puts the rule between the model and the tools.
  Prompt: a suggestion, not a wall
  Deny list: never complete
  If-statement in a tool: knows nothing about order across tools
  Approve everything: nobody reads the 40th dialog
  The gap: a component that knows the HISTORY of calls

  NOTES: Frame it as an ordering problem: 'backup before delete' is a statement about two different tools over time. None of the usual controls have a memory across tools.

SLIDE 5: Petri nets in sixty seconds
------------------------------------------------------------------------------
  [diagram: 03-coffee-net.png]
  Places are cups, tokens are marbles, transitions are machines. The marking is the whole state.
  Enabled: every input cup has a marble
  Fire: take inputs, put outputs
  Two branches in either order, then a join
  A state machine cannot say AND; a DAG has no tokens, so no budgets or locks

  NOTES: This is workflows/coffee/definition.ts, 80 lines. The join needs three marbles at once: that is the thing DAGs cannot express.

SLIDE 6: Every possible future: reachability
------------------------------------------------------------------------------
  [diagram: 04-coffee-reachability.png]
  Breadth-first search over markings. Coffee has 5 states and one terminal state.
  Reachable states = all markings you can get to
  Terminal state = nothing can fire (end, or deadlock)
  Invariant = a weighted token count that never changes
  This enumeration is the whole 'proof' machinery

  NOTES: Say explicitly: the proof technique in this project is exhaustive enumeration of small nets. Nothing symbolic. That is fine for 3-200 states.

SLIDE 7: The trick: a rule becomes a shape
------------------------------------------------------------------------------
  [diagram: 06-rule-require-before.png]
  'require A before B' compiles to three cups and three machines. Reachable states: 3.
  human-approval: a MANUAL transition, 2 states

SLIDE 10: Two products, one library
------------------------------------------------------------------------------
  [diagram: 11-package-layers.png]
  petri-ts (208 lines, external) holds all the mathematics. Engine and gate are built on it.
  Engine: defineWorkflow, guards, executors, Scheduler, SQLite, CLI analyse
  Gate: SkillNet, GateManager, four-phase decision, replay
  Rules: five templates to SkillNets
  Adapters: vercel-ai, agent-sdk, claude-code, openclaw, pi
  Gate depends on engine ^0.1.3: a nested older copy with petri-ts 0.1.6 is live at runtime

  NOTES: The dependency quirk is verified: packages/gate/node_modules/@petriflow/engine is 0.1.3 and bundles petri-ts 0.1.6 while analysis uses 0.2.0. Harmless for these nets, but two copies of the core maths in one install is a smell.

SLIDE 12: One tool call, end to end
------------------------------------------------------------------------------
  [diagram: 13-tool-call-journey.png]
  Four phases: classify, approvals, validate with meta rollback, commit with a re-check.
  Phase 1 per net: free / abstain / gated / blocked
  Any blocked wins; reason text goes to the model
  Phase 2: manual transitions need ctx.confirm; no UI means block
  Phase 3: validateToolCall, meta rolled back on reject
  Phase 4: re-check canFire (TOCTOU), fire or mark pending

  NOTES: packages/gate/src/compose.ts lines 86-187. This is careful code; the compose tests cover rollback and the TOCTOU re-check. Credit where due.

SLIDE 13: Deferred transitions: only believe success you saw
------------------------------------------------------------------------------
  [diagram: 14-deferred-transition.png]
  The call is allowed, the net fires only when the tool RESULT is a success.
  backup is deferred: delete unlocks after backup succeeded
  Error result: pending entry dropped, nothing fires
  isToolResultError lets {ok:false} count as failure (0.4.0)
  No timeout: a hanging tool leaves a pending entry forever

  NOTES: Design is right. Two caveats return as loopholes: examples set isToolResultError to () => false, and nothing expires a pending entry.

SLIDE 15: Five adapters, one core
------------------------------------------------------------------------------
  [diagram: 18-adapters.png]

  vercel-ai: wrap execute; state rebuilt from messages

SLIDE 26: What is real, what is missing
------------------------------------------------------------------------------
  Real and standard:
    Place/transition nets with multiplicity (canFire counts)
    Reachability graph by BFS; terminal states; deadlock flag
    Invariant CHECKING from user-supplied weights
    True concurrency (both interleavings reachable)
    Runtime gate = enabled-transition rule on the marking
    AND composition is sound
  Not there:
    No invariant COMPUTATION (no incidence matrix)
    No boundedness decision: throws at 10,000 states
    No liveness, no temporal logic, no model checker
    Guards stripped before analysis (over-approximation)
    Rules path keeps only the state COUNT
    Composition never analysed; meta/validators invisible

  NOTES: Keep the tone factual. The semantics are textbook. The analysis is minimal. The vocabulary is the problem.

SLIDE 27: Where the mathematics lives
------------------------------------------------------------------------------
  All of it is in petri-ts: 208 lines. This repository implements no analysis algorithm.
  The gate imports only canFire and fire. It never calls reachableStates, analyse or checkInvariant. Its guard field is declared and never evaluated.

  NOTES: packages/gate/src/*.ts imports: canFire, fire. That is the whole runtime relationship to the maths.

SLIDE 28: verifyNets: what 'mathematically verified' means for a rule
------------------------------------------------------------------------------
  // packages/rules/src/compiler.ts, lines 388-396
  function verifyNets(nets: SkillNet<string>[]): NetVerification[] {
    return nets.map((net) => {
      const result = analyse(toPetriNet(net));
      return {
        name: net.name,
        reachableStates: result.reachableStateCount,
      };
    });
  }
  petri-ts also returned isDeadlockFree, terminalStates and invariants. They are discarded. This function cannot fail.
  toPetriNet drops tools, manual/auto, deferred, toolMapper, validateToolCall, meta
  Each net alone, never the AND of all nets
  'verified' = 'we counted 3 states'

  NOTES: This is the single most important slide for the 'fancy word' question. Read it slowly.

SLIDE 38: What 'self-evolving agent' means (two surveys)
------------------------------------------------------------------------------
  Gao et al. 2025/26 (arXiv:2507.21046, TMLR): WHAT evolves (weights, prompts/memory, tools, workflow), WHEN (in-task vs between tasks), HOW (reward, imitation, evolutionary)
  Fang et al. 2025 (arXiv:2508.07407): a loop of inputs -> agent -> environment -> OPTIMISERS that rewrite prompts, memory, tools, workflows or the model
  Working definition: a deployed agent that persistently changes a reusable part of itself from feedback on its own runs
  Both surveys list verification and sandboxing only as FUTURE work

  NOTES: All sources in research/sources.txt; the six most-used were re-fetched to confirm title and numbers.

SLIDE 39: Landmark systems and what evolves
------------------------------------------------------------------------------
  System | What evolves | Result / note
  Reflexion 2023 | episodic text memory | no weight updates
  Voyager 2023 | a library of executable skills | lifelong Minecraft agent
  ADAS 2024 / AFlow ICLR 2025 / MASS ICLR 2026 | whole agent as code / workflow graph / prompts + topology | search over designs

  Darwin Goedel Machine 2025 (ICLR 2026) | its own codebase, archive of variants | SWE-bench 20.0 -> 50.0%; one run FAKED a test log and removed detection markers
  AlphaEvolve 2025 | programs, picked by automated evaluators | the artefact evolves, not the agent
  Huxley-GM, Hyperagents, Red Queen GM 2026 | selection by descendants; the meta-agent itself; agents AND their evaluators | the judge is now inside the loop
  Lean4Agent / LeanEvolve 2026 | workflows revised from formal-verifier output | verifier output as the evolution signal

SLIDE 40: Safety findings specific to self-evolution
------------------------------------------------------------------------------
  Misevolution (Shao et al., ICLR 2026): safety decays INSIDE the improvement loop, no attacker; four pathways: model, memory, tool, workflow
  Benign experience still weakens safety; adding refusal experience causes over-refusal (Findings of ACL 2026)
  Finance audit (arXiv:2608.17684): utility 0.741 -> 0.837 while injection exposure 0.820 -> 0.943
  Verifier tax (Dantas et al., arXiv:2608.14590): blocking 94% of unsafe actions can leave < 5% safe task completion
  Fixed monitors have entropy-bounded recall (arXiv:2608.01388): 68-75% on concentrated attacks, 6-13% on dispersed ones. Loophole L2 in theory
  'Agent Safety Is Action Alignment' (arXiv:2606.28739): enforce least privilege at the action boundary, outside the weights. That is a tool gate

  NOTES: These are the reasons a FIXED gate becomes more relevant as agents evolve, and also the limits of what it can claim.

SLIDE 41: The neighbourhood: formal guardrails for LLM agents
------------------------------------------------------------------------------
  Work | Mechanism | Relation to PetriFlow
  adk-libpetri (GitHub, 2026) | Google ADK agents compiled to Coloured Time Petri nets; Z3 proves deadlock-freedom before execution | closest relative; already has named, checked properties ('proofs are structural and untimed')
  Czejdo et al., DepCoS 2026 | Petri-net reachability for LLM multi-agent synchronisation | same maths, academic
  AgentSpec (ICSE 2026), Progent | trigger-predicate-enforcement DSLs at the tool boundary; Progent allows LLM-generated, dynamically updated policies | same job as the gate, richer predicates
  VeriGuard (ACL 2026) | LLM drafts a policy as code, verified offline, light monitor online | the 'verify then enforce' split PetriFlow claims
  ContrAgent, CaMeLoT, AgentLTL, Agent-C | LTLf/CTL specs compiled to automata or checked with nuXmv/SMT; gate tool calls or steer decoding | temporal properties PetriFlow cannot express

  NOTES: PetriFlow's distinctive bits: the five-template DSL, deferred transitions, and adapters for five frameworks. Its verification story is behind these.

SLIDE 42: Where PetriFlow stands
------------------------------------------------------------------------------
  It does not evolve, by design. That is orthogonal to the frontier, not behind it.
  Grep for evolve / learn / adapt / improve finds nothing in the code. Rules compile once and run unchanged. The research shows safety eroding exactly in the parts that evolve, which makes a fixed gate outside the agent's edit scope more useful, if it can be trusted.

  NOTES: Then pivot: to be that trusted component it needs three things it lacks today.

SLIDE 43: Research agenda that connects the two
------------------------------------------------------------------------------
  # | Direction | What the repo already has | What is missing
  R1 | Rules as the evolvable artefact under a verifier (accept a .rules edit only if composed net is deadlock-free and properties hold) | compile(), per-net enumeration | composed analysis; a property language
  R2 | Monotone safety: adding a rule only tightens; when can a rule be REMOVED safely? | AND composition, addNet/removeNet | a theorem and a check
  R3 | Reachability and block events as an evolution signal for AFlow/DGM-style search | onDecision events, analyse() | a harness
  R4 | Evidence integrity: state from server-observed results, signed history | replay from messages | anything that stops L6
  R5 | Data-aware rules (coloured nets): backup OF x before delete OF x | meta + validateToolCall in JS | DSL syntax and bounded-colour enumeration
  R6 | Classification beyond regex, measured against the entropy bound | map statements | AST or sandbox classifier
  R7 | Guard-aware analysis (SMT over filtrex) so --strict stops over-approximating | toNet, compileGuard | the solver
  R8 | Measure the 0.3.0 claim: do marking-style block messages improve recovery? | formatBlockReason | an experiment

  NOTES: R1, R2 and R4 are the ones that make the gate usable inside a self-evolving system. R5-R8 fix today's loopholes.

SLIDE 44: Conclusions
------------------------------------------------------------------------------
  A real runtime gate: four-phase decision, deferred firing, AND composition, adapters for five frameworks. Small and readable
  Real but minimal mathematics, all in a 208-line external library; the repo adds a terminal-state split and nothing symbolic
  'Formally verified' on the website means 'state count per rule'. No verify command, no invariant check in the rules path, one wrong headline trace
  Six loopholes reproduced by running code; the forged-history one is a design consequence of a stateless gate
  Zero self-evolution in the repo, by design. The literature says that is where a fixed gate is needed, provided composition analysis, a property language and evidence integrity are added
  Recommendation: use the DSL and gate for ordering constraints on tool names; do not cite it as formal verification; pick R1, R2, R4 as the research thread

  NOTES: Close with the recommendation and invite the audience to run labs/loopholes.ts themselves.
